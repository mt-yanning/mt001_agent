▶ AGENTS.md                                    相关度：高   优先级：P0
--------------------------------------------------------------------------------
  作用：Arachne 作者写给「未来在此仓库工作的 AI 助手」的行为规范。
  角色：它不是代码，但定义了这个项目的工程价值观与安全底线。

  对你最重要的四条红线（原文在 Prohibited 一节）：
    1. 不要把真机运动放在默认路径上，必须有显式的 enable/confirm 参数
       → 这解释了 agent_bridge 为什么默认 motion_enabled=false
    2. 不要绕过 Aubo 控制归属（control ownership）与示教模式门控
       → 机械臂同一时刻只能有一个"主人"，抢控制权会出事
    3. 不要提交密钥、日志、编译产物
    4. 不要跑长时间真机测试，除非用户明确确认机器人已就位

  它还定义了「完成标准」：改动要最小、正常入口仍是 teach_panel.launch.py、
  dry-run 路径绝不碰真硬件、提交前要看 git status --short。

  ⚠ 注意：这份文件是给「在 Arachne 仓库里改代码的人」看的。你是在
     mt001_agent/ 里写自己的代码，不改 Arachne，所以主要吸收它的安全思想
     而非字面约束。

▶ config/agent/                                相关度：极高  优先级：P0

  ★★★ 这个目录是「作者已经为 Agent 预留好位置」的铁证。

  ▪ tools.yaml
      内容：10 个工具的名字 + danger 等级 + 一句话描述。
      文件开头注释明确说："本文件是给外部 agent 的文档/配置；ROS 节点
      在 /arachne/agent/tools 上发布同样的工具面。"
      → 你既可以离线读这个 yaml，也可以在线订阅话题，二者等价。

      danger 分级（现成的安全语义，建议你的 Agent 直接沿用）：
        read_only   → get_robot_state
        stop        → safe_stop、arm_stop
        motion      → base_velocity、base_relative、base_turn、
                      arm_cartesian_jog、arm_joint_jog、gripper
        mode_change → aubo_teach

  ▪ agent.example.env
      内容：OPENAI_API_KEY / ANTHROPIC_API_KEY / GEMINI_API_KEY 三个占位，
            外加 ARACHNE_AGENT_MODEL / BASE_URL / LOG_LEVEL。
      关键注释："Provider keys are used by the external agent process,
                not by arachne_agent_bridge."
      → 翻译：桥不碰 API Key，Key 归你的 Agent 进程管。
      → 推荐路径：~/.config/arachne/agent.env，权限 chmod 600。

      ★ 对你的启示：作者设想的架构正是「LLM 大脑在 ROS 之外，通过 JSON
        话题与 ROS 通信」。你的 mt001_agent 完全可以是一个纯 Python 进程，
        不必是 ROS 包（虽然用 rclpy 收发话题最方便）。

▶ docs/step_demo_plan.md                       相关度：高   优先级：P1
--------------------------------------------------------------------------------
  ★ 中文写的重构规划文档，是整个仓库信息密度最高的文档之一。
  角色：它诚实地暴露了这套系统的真实短板，对你设计 Agent 极有参考价值。

  它承认的问题（几乎每一条都是你的 Agent 可以做得更好的地方）：
    · Step Demo 选目标只按 confidence 和 base_x，绕开了最新的 label、
      mask、depth、ROI、reach、IK、collision 和 waypoint 逻辑
    · Step Demo 决策的候选，不一定是 grasp_task_server 实际会抓的候选
      （两个模块各判各的，不同步）
    · 调 /arachne/grasp_task/start 时没有传递或锁定 candidate id / target token
    · 深度相机点云坐标可能存在相机外参/TF 根因问题，不只是精度问题；
      如果 base_grasp_xyz 的坐标系链路错了，approach / too_far 判断
      和最终抓取都会被连带放大
    · 当前主要使用 topdown 抓取和锁定姿态，对瓶罐盒状物是低风险默认策略，
      但不能长期假设所有物体都适合从正上方抓

  ★ 你的 Agent 天然能解决前三条：LLM 大脑统一做目标选择与决策，把
    candidate id 明确传下去，消除"两个模块各判各的"的不一致。
    这可以直接写进你的开源项目动机与论文里。

▶ scripts/                                     相关度：中   优先级：P1
--------------------------------------------------------------------------------
  ⚠ 重要前提：每个 .sh 文件开头都有这行注释——
     "Arachne helper only; not a stable runtime entrypoint."
     作者的意思是：这些脚本随时可能改，别把它们当 API 依赖。
     正确做法是学它们内部调用的 `ros2 launch ...` 命令，直接用 ros2 命令。

  ▪ scripts/env/                               相关度：高   优先级：P0
      arachne_env.sh ....... ★核心环境脚本，必须 source 而非执行
      ros_env.sh ........... ROS 发行版自动探测（jammy→humble，noble→jazzy）
      load_local_env.sh .... 加载 .env.local
      arachne_real_defaults.sh  真机默认参数

      ★★ arachne_env.sh 做的事（与你 CLAUDE.md 里记的 AutoDL 三条命令
         高度相关）：
        1. 从 PATH 和 PYTHONPATH 里剔除所有 .venv / venv / miniconda /
           anaconda / .conda / .pyenv 路径
           → 这正是解决你遇到过的 "No module named catkin_pkg" 的官方做法
        2. unset PYTHONHOME、VIRTUAL_ENV，设 PYTHONNOUSERSITE=1
        3. 强制 ARACHNE_SYSTEM_PYTHON=/usr/bin/python3
        4. 设 FASTDDS_BUILTIN_TRANSPORTS=UDPv4
           （注释说明：FastDDS 共享内存传输会在 Jetson 上留下陈旧锁文件，
             导致 lifecycle 服务调用失败）
        5. source /opt/ros/$ROS_DISTRO/setup.bash 和 install/setup.bash

      ★ 结论：在 AutoDL 上，你可以直接
        `source /root/autodl-tmp/Arachne/scripts/env/arachne_env.sh`
        一条命令替代你现在记的三条。它做的事更全（还处理了 PYTHONPATH
        和 FastDDS）。建议验证后更新你的工作流。

  ▪ scripts/build/                             相关度：中   优先级：P1
      build_workspace.sh ... 全量编译
      build_selected.sh .... 选择性编译单个包（改代码后用这个更快）
      check_workspace.sh ... 编译前检查
      setup_ubuntu.sh ...... x86 Ubuntu 依赖安装  ← AutoDL 用这个
      setup_jetson_humble.sh  Jetson 依赖安装

  ▪ scripts/sim/                               相关度：极高  优先级：P0

▶ src/arachne_gazebo/                          相关度：高   优先级：P1
--------------------------------------------------------------------------------
  包描述：Gazebo-specific helper nodes for the Arachne demo.
  角色：★ C++ 写的 ROS2 ↔ Gazebo 双向桥接，是仿真链路的关键胶水。
  构建系统：ament_cmake（C++，不是 Python）
  依赖：gz-msgs10、gz-transport13  ← ★据此推断对应 Gazebo Garden 代际

  两个可执行文件：

  ▪ gazebo_camera_track_bridge
      作用：控制 Gazebo GUI 摄像机跟随机器人移动。
      参数：offset_topic、target_name（默认 arachne）、follow_pgain（0.85）、
            track_pgain（1.0）、publish_rate（60.0）
      ★ 纯视觉效果，与控制逻辑无关，出问题可以直接关掉
        （with_camera_tracking:=false）

  ▪ gazebo_demo_control_bridge     ★★★ 这个非常重要
      作用：把 ROS2 话题翻译成 Gazebo 内部话题。
      订阅（ROS 侧）：
        /arachne/gripper/command ......... std_msgs/String（open/close/stop）
        /arachne/gui_joint_states ........ sensor_msgs/JointState ★关键
        /arachne/demo/reset .............. std_msgs/Empty
      发布（Gazebo 侧，走 gz-transport 而非 ROS）：
        /arachne/gazebo/ms42dc_left_finger/command   gz.msgs.Double
        /arachne/gazebo/ms42dc_right_finger/command  gz.msgs.Double
        /arachne/gazebo/<6个机械臂关节>/command       gz.msgs.Double
        /model/arachne/joint_trajectory              gz.msgs.JointTrajectory
      其他参数：
        gripper_open_position=0.0、gripper_closed_position=0.6、
        gripper_max_velocity=1.2、publish_rate=60.0
        reset_x=0.0、reset_y=0.0、reset_z=0.22、reset_yaw=0.0
        world_name=arachne_showroom、target_name=arachne

      ★★★ 对你的 Agent 极其重要的发现：
         这个桥订阅 ROS 的 /arachne/gui_joint_states（JointState 消息），
         然后把 6 个关节角度转发给 Gazebo 的位置控制器。
         → 这意味着：在 Gazebo 里，你的 Agent 只要往
           /arachne/gui_joint_states 发一个 JointState 消息，
           机械臂就会动到那个姿态。
         → 这是绕开 agent_bridge 速度指令、在 Gazebo 里直接控制机械臂的
           现成通路。详见【4.6】。

  ▪ 安全状态机（safety_state_machine.py）
      5 个状态：disabled → manual / autonomous → estop → fault
      初始状态：disabled
      关键规则：一旦进入 estop，只能转到 disabled 或保持 estop
                （不能直接从急停跳回运行，必须先 recover）
      发布：/arachne/safety/state （格式 "状态:原因"）
            /arachne/safety/enabled （manual 或 autonomous 时为 true）
      服务：enable / disable / estop / recover / set_manual / set_autonomous

  ▪ hardware_mock.py 详解                      ★★★ 第一个里程碑的主角
      节点名：arachne_hardware_mock
      参数：publish_rate=30.0、wheel_radius=0.16459、track_width=0.58306
            （轮径与轮距与 Gazebo DiffDrive 插件里的数值完全一致）

      订阅（5 个）：
        /cmd_vel ......................... geometry_msgs/Twist
                                           限幅：线速度 [-0.4, 0.8]
                                                 角速度 [-1.4, 1.4]
        /joint_trajectory_controller/joint_trajectory  JointTrajectory
        /aubo_arm_controller/joint_trajectory          JointTrajectory
        /arachne/gripper/command ......... String（open/close/数字）
        /arachne/aubo/teach_command ...... String（teach_on/teach_off）

      发布（5 个 + TF）：
        /odom ............................ nav_msgs/Odometry ★
        /joint_states .................... sensor_msgs/JointState ★
        /arachne/hardware/base_status .... String
        /arachne/hardware/aubo_status .... String
        /arachne/hardware/gripper_status . String
        TF 广播（TransformBroadcaster）

      内部模型：
        · 底盘：差速运动学积分
          x += vx·cos(yaw)·dt ；y += vx·sin(yaw)·dt ；yaw += wz·dt
          左右轮转角 = (vx ∓ wz·track_width/2) / wheel_radius · dt 累加
        · 机械臂：从当前位置向目标位置线性插值，时长取自轨迹点的
          time_from_start
        · 夹爪：open→0.0，close→0.6，数字→(1 - n/19656)·0.6

      HOME 姿态（6 个关节，弧度，全仓库多处复用这组数值）：
        aubo_shoulder_joint  = -1.5707963267949
        aubo_upperArm_joint  =  0.201570428261868
        aubo_foreArm_joint   =  1.65970467002488
        aubo_wrist1_joint    =  0.485178041391533
        aubo_wrist2_joint    =  1.67675136677345
        aubo_wrist3_joint    =  0.76432946885334

      ★★★ 致命细节（直接决定你第一个里程碑的预期）：
         mock 只订阅 JointTrajectory 类型的机械臂指令，
         【不订阅】/arachne/aubo/joint_velocity_command。
         而 agent_bridge 的 arm_cartesian_jog / arm_joint_jog 恰恰只发
         joint_velocity_command。
         → 结论：mock 下机械臂点动工具发出去没人接，假机械臂不会动。
           详见【8.2】的完整能力矩阵。

  ▪ mock_bringup.launch.py
      只启动 3 个节点（其中 1 个默认关闭）：
        arachne_safety_state_machine  （安全状态机）

      关键默认值（备查）：
        use_scout=true、use_ms42dc=true、use_aubo=true
        use_aubo_ros2_driver=false  ★说明作者用自写驱动而非官方驱动
        scout_driver=waveshare、scout_usb_baudrate=2000000
        scout_can_bitrate=500000
        ms42dc_driver=direct、ms42dc_baudrate=115200
        ms42dc_open_angle_tenths=19656、ms42dc_close_angle_tenths=19656
        aubo_robot_ip=192.168.127.128、aubo_port=30004、aubo_rpc_port=30004

  ▪ AuboMoveJoint.action              相关度：中

4.5 ★★★ Gazebo 仿真的三个致命限制（README 完全没写）
--------------------------------------------------------------------------------

  【限制一】ROS 侧收不到 /joint_states
      原因：ros_gz_bridge 的桥接列表里没有 joint_states。
      后果：任何依赖 /joint_states 的节点在 Gazebo 演示下都拿不到数据。
      ★ 对 agent_bridge 的直接影响：
        agent_bridge._current_arm() 会抛 "no complete Aubo joint state"，
        导致 arm_cartesian_jog 和 arm_joint_jog 【必然失败】。
      ★ autopick 规划器怎么绕开的：
        它不读关节反馈，而是自己在内存里维护 self.current_arm，
        每个控制周期算目标、限速、然后发出去。
        → 这是【开环控制】。仿真里能跑通是因为 Gazebo 的位置控制器
          足够听话，真机上这么做会很危险。

  【限制二】odom 话题名不一致
      Gazebo 发的是 /gz/odom，agent_bridge 默认订阅 /odom。
      → 必须重映射，否则 agent_bridge 永远拿不到底盘位姿。

  【限制三】机械臂控制协议不通用
      Gazebo 侧：/arachne/gazebo/<joint>/command，std_msgs/Float64，
                 【位置】控制
      真机侧：  /arachne/aubo/joint_velocity_command，
                 Float64MultiArray，【速度】控制
      agent_bridge 只会发后者。
      → agent_bridge 的机械臂工具在 Gazebo 下【完全无效】。

  ★★★ 但是有一条现成的救命通路（见 4.6）


4.6 ★★★ Gazebo 下控制机械臂的正确姿势
--------------------------------------------------------------------------------
  gazebo_demo_control_bridge 订阅 ROS 话题 /arachne/gui_joint_states
  （类型 sensor_msgs/JointState），并把其中的 6 个关节角度转发给
  Gazebo 的位置控制器。

  → 结论：你的 Agent 在 Gazebo 里控制机械臂，应该发布 JointState 到
    /arachne/gui_joint_states，而不是走 agent_bridge 的点动工具。

  数据流：
      你的 Agent
        │  发布 sensor_msgs/JointState
        ↓
      /arachne/gui_joint_states  (ROS 话题)
        │
        ↓
      gazebo_demo_control_bridge  (C++ 节点，订阅 ROS，发布 gz)
        │  转成 gz.msgs.Double × 6
        ↓
      /arachne/gazebo/<joint>/command  (gz 内部话题)
        │
        ↓
      JointPositionController 插件 × 6
        │
        ↓
      Gazebo 里的机械臂真的动了

  同理，夹爪：
      你的 Agent → /arachne/gripper/command (String: open/close/stop)
                 → gazebo_demo_control_bridge
                 → /arachne/gazebo/ms42dc_{left,right}_finger/command
                 → 夹爪张合
      ★ 这条路 agent_bridge 的 gripper 工具正好也是发
        /arachne/gripper/command，所以【夹爪工具在 Gazebo 下是有效的】。

  ⚠ 但要注意：/arachne/gui_joint_states 是【绝对关节角度】，
    不是相对增量。你的 Agent 需要自己维护当前姿态并做插值，
    否则机械臂会瞬移（Gazebo 位置控制器会尽力追，但会很暴力）。
    autopick 规划器里的 _step_arm_toward_target() 就是干这个的，
    可以直接借鉴它的限速逻辑（arm_joint_speed=0.55 rad/s）。

5.1 定位与设计哲学
--------------------------------------------------------------------------------
  包描述：Safe task and teach-control bridge for external Arachne agents.

  源码里的类文档字符串（agent_bridge.py:128-133）直接说明了设计意图：
    "Bounded teach-control bridge for an external agent.
     The bridge exposes a small JSON tool surface. It deliberately does not
     load API keys or talk to an LLM provider; external agent processes call
     this node after they have made a task decision."

  中文翻译与解读：
    · "Bounded"（有界的）——所有指令都被夹紧在安全范围内
    · "teach-control"（示教级控制）——只做小幅点动，不做大范围规划
    · "deliberately does not load API keys"（刻意不加载 API Key）
      ★ 这是给你划的分工线：桥只管安全执行，LLM 推理归你的进程管
    · "after they have made a task decision"（在你做出决策之后）
      ★ 桥不做决策，它只是一个安全的执行末端

  ★★ 这个分工对你极其有利：
     你不需要写 ROS 驱动、不需要处理限速、不需要管急停，
     你只需要写「理解人话 → 输出 JSON」这一层。

5.5 指令 JSON 格式
--------------------------------------------------------------------------------

  ▪ 基本格式
      {"tool": "<工具名>", "<参数名>": <值>, ...}

  ▪ 容错设计（agent_bridge.py:257-296）
      1. 空字符串 → 直接忽略，不报错
      2. JSON 解析失败 → 把整个字符串当作工具名
         例：发送 "safe_stop" 等价于 {"tool": "safe_stop"}
      3. "tool" 字段缺失时，回退读 "command" 字段
      4. 工具名自动转小写、去空格
      5. 支持一套别名映射：
            state, status      → get_robot_state
            stop               → safe_stop
            base_move          → base_velocity
            base_cmd_vel       → base_velocity
            drive_relative     → base_relative
            turn_relative      → base_turn
            arm_xyz, tcp_jog   → arm_cartesian_jog
            joint_jog          → arm_joint_jog
            open_gripper       → gripper（自动补 command="open"）
            close_gripper      → gripper（自动补 command="close"）
            teach              → aubo_teach

      ★ 这套容错对 LLM 极其友好：LLM 输出的工具名稍有偏差也能被接住。
        ★ 但你的 Agent 应该始终输出规范名，别依赖别名——
          规范名是 tools 话题里公布的，别名是未文档化的实现细节。

  ▪ 参数别名（每个工具都支持多种写法）
      base_velocity:      linear_x / vx      angular_z / wz
                          duration_sec / duration
      base_relative:      distance_m / distance
      base_turn:          angle_deg / angle / angle_rad（自动转度）
      arm_cartesian_jog:  vector[3] 或 x/y/z 或 axis+distance_m+sign
                          speed_m_s、duration_sec
      arm_joint_jog:      joint / index      delta_rad / delta
                          speed_rad_s、duration_sec
      gripper:            command / state
      aubo_teach:         enabled / value

5.6 ★ 10 个工具完整规格

  ┌──────────────────────────────────────────────────────────────────────┐

  └──────────────────────────────────────────────────────────────────────┘

  └──────────────────────────────────────────────────────────────────────┘

    参数：无

          ⑤ 发 {"command":"stop"} 到 grasp_task base_command

    ★★ 你的 Agent 应该在任何异常、超时、不确定的情况下无条件调用它。

  ┌──────────────────────────────────────────────────────────────────────┐

  └──────────────────────────────────────────────────────────────────────┘
    JSON：{"tool": "arm_stop"}
    作用：只发 4 次零速到机械臂，不碰底盘和夹爪。
    安全门：无

  ┌──────────────────────────────────────────────────────────────────────┐
  │ 4. base_velocity                            danger: motion           │
  └──────────────────────────────────────────────────────────────────────┘
    JSON：{"tool":"base_velocity", "linear_x":0.1, "angular_z":0.0,
           "duration_sec":1.0}
    参数：

      angular_z    角速度 rad/s，夹紧到 ±max_base_angular_z（默认 0.35）
      duration_sec 持续时间，夹紧到 [0.05, max_base_command_duration_sec]
                   （默认上限 2.0 秒），缺省值 0.2
    作用：设置一个「活跃底盘速度」，由定时器持续发布，到期自动归零。

    返回：{"ok":true, "message":"base velocity active for 1.00s",

  └──────────────────────────────────────────────────────────────────────┘

    参数：distance_m，夹紧到 ±max_base_relative_distance_m（默认 0.30）
    作用：★不直接控制底盘，而是转发一条 JSON 到
          /arachne/grasp_task/base_command：
            {"command":"drive_relative", "distance_m":0.1}
    安全门：motion_enabled ✓ + confirm_agent_motion ✓

       agent_bridge 【不会】告诉你没人接——它照样返回 ok:true。

  │ 6. base_turn                                danger: motion           │
  └──────────────────────────────────────────────────────────────────────┘
    JSON：{"tool":"base_turn", "angle_deg":10.0}
      或：{"tool":"base_turn", "angle_rad":0.1745}   （自动转成度）
    参数：angle_deg，夹紧到 ±max_base_relative_yaw_deg（默认 30.0）
    作用：转发 {"command":"turn_relative","angle_deg":10.0}
    安全门与依赖：同 base_relative

  ┌──────────────────────────────────────────────────────────────────────┐
  │ 7. arm_cartesian_jog                        danger: motion           │
  └──────────────────────────────────────────────────────────────────────┘
    JSON 三种写法：
      {"tool":"arm_cartesian_jog", "axis":"z", "distance_m":0.01}
      {"tool":"arm_cartesian_jog", "x":0.01, "y":0.0, "z":0.02}
      {"tool":"arm_cartesian_jog", "vector":[0.01, 0.0, 0.02]}
    参数：
      axis         "x"/"y"/"z"（base_link 坐标系）
      sign         方向，默认 1.0
      distance_m   位移，缺省时用 max_arm_cartesian_step_m
      speed_m_s    速度，默认 arm_cartesian_speed_m_sec（0.015 m/s）
      duration_sec 可显式指定，否则 = 距离 / 速度
    夹紧：位移模长 > max_arm_cartesian_step_m（默认 0.03 m）时按比例缩放
    作用：★★算法是这样的——
          ① 读当前 6 关节角（要求新鲜，见下方"新鲜度检查"）
          ② 构造 6 维 twist 向量，前 3 维 = 位移/时长，后 3 维（角速度）= 0
          ③ 用数值差分求 6×6 雅可比矩阵（每个关节 +1e-5 扰动做 FK）
          ④ 阻尼最小二乘解关节速度：
               q̇ = Jᵀ · (J·Jᵀ + λ²·I)⁻¹ · twist
               其中 λ = arm_velocity_damping（默认 0.08）
          ⑤ 峰值限速到 arm_velocity_max_joint_speed_rad_sec（默认 0.18）
          ⑥ 激活为「活跃机械臂速度」，由 80 Hz 定时器持续发布
    安全门：motion_enabled ✓ + confirm_agent_motion ✓
    ★ 数学原理：阻尼最小二乘（DLS / Levenberg-Marquardt）逆运动学。
      加 λ²I 是为了在奇异位形附近避免关节速度爆炸——这是牺牲少量
      末端精度换取数值稳定性的经典做法。

  ┌──────────────────────────────────────────────────────────────────────┐
  │ 8. arm_joint_jog                            danger: motion           │
  └──────────────────────────────────────────────────────────────────────┘
    JSON：{"tool":"arm_joint_jog", "joint":"wrist3_joint", "delta_rad":0.03}
    参数：
      joint      关节标识，支持 4 种写法：
                   规范名   "wrist3_joint"
                   带前缀   "aubo_wrist3_joint"
                   J 记号   "J6"（1-based）
                   索引     0-5 或 "0"-"5"
      delta_rad  相对角度，夹紧到 ±max_arm_joint_step_rad（默认 0.12）
      speed_rad_s  默认 arm_joint_speed_rad_sec（0.06）
      duration_sec 可显式指定，否则 = |delta| / speed
    作用：只让一个关节动，速度 = delta / duration，其余关节速度为 0。
    安全门：motion_enabled ✓ + confirm_agent_motion ✓

      索引 1  upperArm_joint  ← aubo_upperArm_joint, upper_arm_joint
      索引 2  foreArm_joint   ← aubo_foreArm_joint, fore_arm_joint
      索引 3  wrist1_joint    ← aubo_wrist1_joint
      索引 4  wrist2_joint    ← aubo_wrist2_joint
      索引 5  wrist3_joint    ← aubo_wrist3_joint
      ★ 注意大小写：upperArm 和 foreArm 是驼峰！写成 upperarm 会失败。

  └──────────────────────────────────────────────────────────────────────┘

    作用：发 String 到 /arachne/gripper/command
    安全门：motion_enabled ✓ + confirm_agent_motion ✓

  │ 10. aubo_teach                              danger: mode_change      │
  └──────────────────────────────────────────────────────────────────────┘
    JSON：{"tool":"aubo_teach", "enabled":true}
    参数：enabled（布尔）
    作用：发 "teach_on" / "teach_off" 到 /arachne/aubo/teach_command

5.7 ★★ 安全机制的四层设计
--------------------------------------------------------------------------------

  【第一层】开关门控（_require_motion_allowed，agent_bridge.py:323-327）
      所有 danger=motion 的工具，进入前必须通过：
        motion_enabled == true       否则抛 PermissionError
        confirm_agent_motion == true 否则抛 PermissionError
      aubo_teach 额外需要 allow_mode_change == true
      ★ 三个开关默认全 false，且 launch 文件默认也全 false。
        必须在命令行显式 :=true 才能生效。

  【第二层】参数硬夹紧（每个工具内部）
      即使你发 linear_x=100，也会被 _clamp 到 0.20。
      即使你发 duration_sec=9999，也会被夹到 2.0。
      ★ 夹紧是静默的——不报错，只是把值改小。
        你的 Agent 要从返回的 data 字段读实际生效值，
        而不是假设发什么就是什么。

  【第三层】超时自动归零（_publish_active_motion，agent_bridge.py:581-600）
      桥内部维护 active_until 时间戳，一个 80 Hz 定时器
      （arm_velocity_publish_rate=80.0）持续做：
        · 如果当前时间 > active_until → 清空状态，发零速给底盘和机械臂
        · 否则 → 重复发布当前活跃速度
      ★★ 这是「死人开关」（deadman switch）设计：
         即使你的 Agent 进程崩溃、网络断开，机器人也会在
         duration_sec 到期后自动停下，最长 2 秒。
      ★ 副作用：底盘速度指令是【持续发布】的，不是发一次就完。
        这符合 ROS 惯例（cmd_vel 通常要持续发，否则驱动会超时保护）。

  【第四层】关节状态新鲜度检查（_current_arm，agent_bridge.py:525-539）
      两个机械臂工具执行前必须拿到「新鲜」的关节状态：
        · 6 个关节必须全部齐全，否则抛 "no complete Aubo joint state"
        · 如果 require_fresh_joint_states=true（默认），
          状态年龄必须 ≤ fresh_state_timeout_sec（默认 2.0 秒），
          否则抛 "Aubo joint state is stale: X.XXs"
      ★★ 这就是为什么 Gazebo 下机械臂工具必然失败（没有 /joint_states）。
      ★ 如果你要在 Gazebo 下强行用这两个工具，可以设
        require_fresh_joint_states:=false —— 但【强烈不建议】，
        因为没有关节状态就无法算雅可比，会拿到全零或错误的结果。

  【额外】敏感信息脱敏（_redacted，agent_bridge.py:712-724）
      事件发布前，会递归遍历指令内容，把 key 中包含
      "key" / "token" / "secret" / "password" 的字段值替换成 "<redacted>"。
      ★ 说明作者预料到 Agent 可能不小心把 API Key 塞进指令里。

7.1 基本信息
--------------------------------------------------------------------------------
  路径：src/arachne_demo/arachne_demo/gazebo_autopick_planner.py
  规模：759 行，纯 Python，★零第三方依赖（连 numpy 都不用）
  节点名：gazebo_autopick_planner
  类名：GazeboAutoPickPlanner

  源码里的文档字符串（第 70-79 行）值得逐句读：
    "Known-world autonomy validation for the Gazebo showroom.
     This node intentionally keeps the planner dependency-free. The base uses
     a continuously refreshed grid A* path over the known SDF showroom
     geometry, then follows it with a pure-pursuit style controller. The arm
     does not play a prewritten trajectory: every control tick computes a
     target joint pose from the current base pose and the target object pose,
     then rate-limits the command toward that pose. This is a simulation
     validation layer; the same launch contract can later be backed by
     MoveIt2 and ros2_control."

  ★ 关键词 "Known-world"（已知世界）—— 作者自己承认这是「上帝视角」方案。
  ★ 关键词 "This is a simulation validation layer"（这只是仿真验证层）
    —— 作者自己就说了这不是最终方案。
  ★★ 这段话就是你项目立项的最佳引用：作者明确留出了升级空间。

7.2 它现在怎么工作
--------------------------------------------------------------------------------

  ▪ 输入
      只订阅一个话题：/gz/odom（底盘位姿）
      ★★ 没有任何感知输入。没有相机、没有雷达、没有点云。

  ▪ 输出（4 类）
      /cmd_vel ..................... 底盘速度
      /arachne/gui_joint_states .... 机械臂关节角（JointState）
      /arachne/gazebo/<joint>/command × 6 ... 机械臂关节角（Float64，冗余发送）
      /arachne/gripper/command ..... 夹爪

  ▪ 世界模型：★★★ 完全硬编码
      目标物体坐标写死在参数默认值里：
        target_x = 3.40, target_y = -2.35, target_z = 0.38
        approach_x = 2.62, approach_y = -2.35, approach_standoff = 0.76
      8 个障碍物写死在 _known_obstacles() 方法里（第 177-187 行）：
        demo_pedestal    (-1.20, -1.40)  半径 0.58
        soft_target_box  ( 1.00, -1.50)  半径 0.45
        marker_column    (-2.00,  1.40)  半径 0.38
        slalom_marker_a  (-1.40,  2.10)  半径 0.32
        slalom_marker_b  (-0.40,  1.55)  半径 0.32
        slalom_marker_c  ( 0.60,  2.10)  半径 0.32
        work_table       ( 2.45,  1.70)  半径 0.62
        inspection_crate ( 3.45,  0.25)  半径 0.50
      场地边界写死：bounds = (-5.4, 5.4, -3.55, 3.55)

      ★★ 这些坐标是【手工从 arachne_showroom.sdf 抄过来的】。
         world 文件一改，这里就失效，而且不会报错——机器人会撞上去。

  ▪ 底盘导航算法
      栅格 A*（grid_resolution = 0.16 m）
        · _world_to_cell / _cell_to_world 做坐标转换
        · _blocked 判断格子是否被障碍占据
          （膨胀半径 = robot_radius 0.48 + obstacle_clearance 0.18）
        · _nearest_free_cell 处理起点/终点在障碍里的情况
        · _heuristic 欧氏距离启发
        · _reconstruct 回溯路径
        · _smooth_path + _segment_is_clear 做路径平滑（视线剪枝）
      纯追踪（Pure Pursuit）跟随
        · lookahead_distance = 0.46 m
        · linear_speed = 0.42 m/s，angular_speed = 1.05 rad/s
        · position_tolerance = 0.12 m，yaw_tolerance = 0.16 rad
      周期重规划：replan_period = 0.75 秒
      控制频率：publish_rate = 30 Hz

  ▪ 机械臂算法：★自写正/逆运动学
      正运动学（FK）：
        用 4×4 齐次变换矩阵链乘，全部用嵌套 list 手写实现
        （_matmul、_translation、_rpy_matrix、_rotation_x/y/z）
        DH 参数写死在 AUBO_JOINT_ORIGINS（6 组 xyz + rpy）：
          (0.0, 0.0, 0.122),   rpy (0, 0, π)
          (0.0, 0.1215, 0.0),  rpy (-π/2, -π/2, 0)
          (0.408, 0.0, 0.0),   rpy (-π, 0, 0)
          (0.376, 0.0, 0.0),   rpy (π, 0, π/2)
          (0.0, 0.1025, 0.0),  rpy (-π/2, 0, 0)
          (0.0, -0.094, 0.0),  rpy (π/2, 0, 0)
        机械臂安装：ARM_MOUNT_XYZ = (0.22, 0.0, 0.105)
                    ARM_MOUNT_RPY = (0.0, 0.0, π/2)
        末端偏移：GRASP_FRAME_OFFSET = 0.165 m
        TOOL0_RPY = (0.0, 0.0, π/2)
      逆运动学（IK）：
        _solve_ik_position —— 只解位置（3 自由度），不管姿态
        方法：有限差分雅可比 + 阻尼最小二乘迭代
              IK_MAX_STEP = 0.08，IK_DAMPING = 0.08，IK_EPSILON = 1e-4
        ★ 只用 3×3 的位置雅可比 + _inverse_3x3 手写求逆
      ★★ 开环控制：不读 /joint_states，自己在 self.current_arm 里
         维护「我以为的关节角」，每周期向目标插值
         （arm_joint_speed = 0.55 rad/s，arm_tolerance = 0.045 m）

  ▪ 状态机（self.state 和 self.arm_phase 同步推进）
      wait_odom  → 等第一帧里程计
        ↓
      navigate   → A* 路径跟随，到达 approach 点
        ↓
      align      → 原地转向对准目标
        ↓
      pre_grasp  → 机械臂移到目标上方
        ↓
      grasp      → 机械臂下探到目标
        ↓
      close      → 闭合夹爪
        ↓
      lift       → 抬起
        ↓
      return     → 回 HOME 姿态
        ↓
      done       → 结束

      ★ 每个阶段的切换条件是「末端位置误差 < arm_tolerance（0.045 m）」
        或超时。

  ▪ 关键姿态常量
      HOME_POSE  = [-1.5707963267949, 0.201570428261868, 1.65970467002488,
                    0.485178041391533, 1.67675136677345, 0.76432946885334]
      READY_POSE = [1.38, -0.22, -1.10, 0.12, -1.38, 0.0]

  ▪ 其他参数
      auto_start = True   ★启动后自动开跑，不等任何触发

7.3 它的六个根本缺陷
--------------------------------------------------------------------------------
  ① 零感知
     不订阅任何传感器。目标坐标是人给的，不是看到的。
     → 目标一旦移动，它完全不知道。

  ② 零语义
     不理解「瓶子」是什么，只知道 (3.40, -2.35, 0.38) 这个数。
     → 无法处理「把红色的那个拿过来」。

  ③ 世界模型手工同步
     8 个障碍物坐标是从 SDF 手抄的，两处数据没有任何自动同步机制。
     → 场景一改就失效，且静默失效。

  ④ 单一固定任务
     只能做「走到瓶子那里抓起来」这一件事。
     换目标要改参数重启，换任务要改代码。

  ⑤ 无失败恢复
     状态机是单向的，没有任何回退分支。
     抓空了、撞上了、IK 解不出来——它不知道，会继续往下走。

  ⑥ 开环控制
     不读关节反馈，假设指令一定被完美执行。
     仿真里能糊弄过去，真机上是安全隐患。

7.4 ★★★ 你的 Agent 怎么替换它
--------------------------------------------------------------------------------

  ▪ 替换的物理操作：一个 launch 参数
        ros2 launch arachne_demo gazebo_autopick_demo.launch.py \
            with_autopick:=false

      这会让 autopick 节点不启动，Gazebo 里的机器人变成「无人驾驶」状态，
      等着你的 Agent 接管。其余节点（spawn、bridge、相机跟随、
      相机轨道、★demo_control_bridge）照常运行。

      ★★ 特别注意：demo_control_bridge 是【无条件启动】的
         （launch 文件里它没有 condition），这正是你需要的——
         它提供了 /arachne/gui_joint_states 和 /arachne/gripper/command
         这两条通往 Gazebo 的控制通路。

  ▪ 接管后你需要自己提供的能力（按优先级排序）

      【必须，第一阶段】底盘移动
        方案：直接发 /cmd_vel，或走 agent_bridge 的 base_velocity
        ★ 走 agent_bridge 更好——白拿限速、超时归零、状态反馈三件套
        ★ 记得处理 odom 话题名（/gz/odom vs /odom，见 5.8）

      【必须，第一阶段】夹爪
        方案：发 /arachne/gripper/command，或走 agent_bridge 的 gripper 工具
        ★ 两条路等价，agent_bridge 最终也是发这个话题

      【必须，第二阶段】机械臂
        ★★ 不能用 agent_bridge 的机械臂工具（Gazebo 下无效，见 4.5）
        方案：发 sensor_msgs/JointState 到 /arachne/gui_joint_states
        你需要自己实现：
          · FK（算末端在哪）—— 可以复用
            arachne_operator.real_hardware_acceptance_test.AuboI5Kinematics
            （agent_bridge 就是这么干的），或者抄 autopick 里的实现
          · IK（算关节角）—— 抄 autopick 的 _solve_ik_position 最省事
          · 限速插值 —— 抄 autopick 的 _step_arm_toward_target
        ★ 建议：把 autopick 里的运动学部分【原样搬到你的仓库】当工具库，
          只重写决策层。这样你的工作量集中在真正有价值的地方。

      【可选，第三阶段】感知
        ★ 当前 Gazebo 没有相机（见 6.7、9.3）。
        三个选项：
          A. 不做感知，用「上帝视角」提供物体列表给 LLM
             （诚实地在文档里标注这是简化假设）
          B. 给 URDF 加相机 + 给 ros_gz_bridge 加图像话题，
             接 YOLO（yolo_workspace 里有现成权重）
          C. 用 Gazebo 的场景状态服务查询物体真实位姿，
             模拟「完美感知」
        ★ 两个月项目建议先做 A，有余力再做 B。

  ▪ 两条实现路线的对比（对应你 CLAUDE.md 里记的两条路）

      ┌──────────────────────────────────────────────────────────────┐
      │ 路线一：低层遥操（Agent 直接发点动指令）                      │
      └──────────────────────────────────────────────────────────────┘
        做法：with_autopick:=false，Agent 通过 agent_bridge 发
              base_velocity / gripper，通过 gui_joint_states 控机械臂
        优点：· 完全掌控，每一步都是 Agent 决策
              · 在 mock 下就能验证大部分链路
              · 能充分展示 LLM 的分解能力（"前进 → 转向 → 伸手 → 闭合"）
        缺点：· 需要自己实现 IK 与运动规划
              · LLM 调用次数多，延迟累积
              · 容易在低层细节上耗掉两个月
        ★ 适合：第一个可演示版本

      ┌──────────────────────────────────────────────────────────────┐
      │ 路线二：高层任务编排（Agent 调 grasp_task_server）            │
      └──────────────────────────────────────────────────────────────┘
        做法：Agent 只负责「选哪个目标、要不要靠近、放弃还是重试」，
              具体抓取交给已验证的 grasp_task_server
        优点：· 复用真机验证过的抓取逻辑，成功率有保障
              · LLM 只在决策点介入，延迟低
              · 更接近 BUMBLE 那种「分层技能」的架构
        缺点：· grasp_task_server 依赖真实感知（YOLO + 深度相机），
                在当前 Gazebo 环境里跑不起来
              · 需要额外启动 grasp_task_server 节点
        ★ 适合：最终形态，但需要先解决 Gazebo 感知问题

      ★★ 建议走【混合路线】——
         · 底盘用高层（base_relative / base_turn，走 grasp_task_server）
         · 机械臂用低层（gui_joint_states + 自己的 IK）
         · 感知先用「上帝视角」桩（stub），架构上留好接口
         这样两个月内能出一个完整可演示的东西，
         同时架构上对接真实感知是开放的。

  ▪ 你的 Agent 相对 autopick 的六个改进点（写进 README/论文）
      autopick 的缺陷            →  你的 Agent 的改进
      ────────────────────────────────────────────────────────────
      ① 零感知                   →  接入感知接口（哪怕先是桩）
      ② 零语义                   →  LLM 理解自然语言指令
      ③ 世界模型手工同步          →  从场景动态获取/由 LLM 维护
      ④ 单一固定任务             →  多任务，任务由人话定义
      ⑤ 无失败恢复               →  LLM 观察状态，判断重试/换目标/放弃
      ⑥ 开环控制                 →  闭环，读 status 后再决策

      ★★ 第 ⑤ 条是你的 Agent 最有说服力的差异点，
         也正好对应 docs/step_demo_plan.md 里作者自己吐槽的痛点。
         建议把「失败恢复」设计成你项目的核心卖点。

  失败模式详解（★★这部分极其重要，决定你 Agent 的设计）：

    · base_relative / base_turn 在 mock/Gazebo 下：
      agent_bridge 会返回 ok:true「command forwarded」，
      但 /arachne/grasp_task/base_command 上没有订阅者，指令消失。
      ★★ 这是【静默失败】——你的 Agent 会以为成功了。
      ★ 解决：额外启动 grasp_task_server（见 8.4 的组合 C）

    · arm_cartesian_jog / arm_joint_jog 在 mock 下：
      mock 【有】发 /joint_states，所以新鲜度检查能通过。
      指令会成功计算出关节速度并发布到
      /arachne/aubo/joint_velocity_command，agent_bridge 返回 ok:true，
      但 mock 不订阅这个话题，所以假机械臂不动。
      ★★ 也是【静默失败】，而且比上面那个更隐蔽。

    · arm_cartesian_jog / arm_joint_jog 在 Gazebo 下：
      会抛 RuntimeError "no complete Aubo joint state"（因为无 /joint_states）
      ★ 这个反而是【显式失败】，agent_bridge 会返回 ok:false。

  ★★★ 这张表的结论：
     你的 Agent 在设计时【绝不能假设 ok:true 就等于机器人真的动了】。
     必须通过 /arachne/agent/status 里的 latest.odom / arm_joints
     实际观察状态变化来确认。
     ★ 这个「发指令 → 观察 → 确认」的闭环，本身就是你 Agent 的核心价值，
       也正好是 autopick 缺的东西。

9.1 编译相关
--------------------------------------------------------------------------------
  ▪ conda 劫持问题的官方解法
      scripts/env/arachne_env.sh 会自动从 PATH 和 PYTHONPATH 里剔除
      .venv / venv / miniconda / anaconda / .conda / .pyenv 路径，
      并 unset PYTHONHOME 和 VIRTUAL_ENV，设 PYTHONNOUSERSITE=1。
      ★ 这比手动 grep -v miniconda 更彻底。建议在 AutoDL 上直接用它。

  ▪ 编译依赖链
      arachne_agent_bridge → 依赖 arachne_operator（导入 AuboI5Kinematics）
      arachne_demo（Gazebo launch）→ 运行时依赖 arachne_description、
        aubo_description、scout_description、dh_ag95_description
        ★★ 这 4 个包必须都编译成功，否则 launch 在计算
           GZ_SIM_RESOURCE_PATH 时就会抛异常，与是否用 ag95 夹爪无关。
      arachne_sim → 依赖 arachne_operator（AuboI5Kinematics + grasp_geometry）
      arachne_gazebo → 依赖 gz-msgs10 / gz-transport13（C++ 编译期依赖）

  ▪ 增量编译
      改代码后不必全量编译：
        ./scripts/build/build_selected.sh <包名>
      Python 包甚至可以用 symlink 安装避免重复编译：
        colcon build --symlink-install --packages-select arachne_agent_bridge

  ▪ FastDDS 传输设置
      arachne_env.sh 设了 FASTDDS_BUILTIN_TRANSPORTS=UDPv4。
      原因（源码注释）：FastDDS 共享内存传输会在 Jetson 上留下陈旧锁文件，
      导致 lifecycle 服务调用失败。
      ★ 在服务器上如果遇到「服务调用卡住不返回」，先检查这个环境变量。

  ▪ ROS 发行版自动探测
      scripts/env/ros_env.sh 会根据 /etc/os-release 的 UBUNTU_CODENAME
      自动选择：jammy → humble（首选）/ jazzy，noble → jazzy / humble。
      也可以手动 export ROS_DISTRO=humble 覆盖。

9.2 Gazebo 启动相关
--------------------------------------------------------------------------------
  ▪ 必须的系统依赖
      ros_gz_sim、ros_gz_bridge（Humble 上包名可能是 ros-humble-ros-gz-*）
      xacro
      ★ 验证命令：
        ros2 pkg list | grep ros_gz
        ros2 pkg prefix ros_gz_sim
      ★ 若缺失：sudo apt install ros-humble-ros-gz

  ▪ ★★★ Gazebo 版本核实（这可能是你的第一个大坑）
      源码依赖 gz-msgs10 / gz-transport13，推断为 Gazebo Garden。
      ⚠ ROS2 Humble 官方配套的是 Gazebo Fortress
        （gz-msgs9 / gz-transport12），Garden 需要额外的 apt 源。
        如果版本对不上，arachne_gazebo 这个 C++ 包会编译失败。

      ★ 在服务器上核实：
        gz sim --version
        apt list --installed 2>/dev/null | grep -E "gz-(msgs|transport)"
        ros2 pkg list | grep arachne     ← ★看 arachne_gazebo 在不在

      ★★ 你 CLAUDE.md 里说「已成功编译 11 个包」——但 src 下有 12 个
        自研包（含 vendor 空壳）。如果没编成功的恰好是 arachne_gazebo，
        Gazebo 演示就跑不起来（因为 demo_control_bridge 和
        camera_track_bridge 都在这个包里）。
        ★★★ 建议第一件事就是核实这一点。

  ▪ 无头（headless）运行
      ⚠ README 和所有 launch 文件都【没有】提供无头模式参数。
      默认 gz_args = "-r -v 1 -z 180 --render-engine ogre2
                      --render-engine-api-backend opengl <world>"
      要无头运行需要手动覆盖整个 gz_args：
        # 先拿到 world 的绝对路径
        WORLD=$(ros2 pkg prefix arachne_demo)/share/arachne_demo/worlds/arachne_showroom.sdf
        ros2 launch arachne_demo gazebo_autopick_demo.launch.py \
          gz_args:="-r -s -v 1 -z 180 $WORLD" \
          with_camera_tracking:=false
      其中 -s = server only（不起 GUI）
      ⚠ 无头时相机跟随失去意义，所以同时关掉 with_camera_tracking

  ▪ 软件渲染（无 GPU 时）
      export LIBGL_ALWAYS_SOFTWARE=1
      ⚠ 会非常慢（180Hz 物理步进 + 软渲染基本跑不动）
      ★ AutoDL 有 RTX 3080 Ti，应该能硬件渲染，但需要确认
        显卡驱动和 OpenGL 可用：
          nvidia-smi
          glxinfo | grep "OpenGL renderer"
        （glxinfo 需 apt install mesa-utils）
      ★ AutoDL 这类云服务器通常没有物理显示器，
        大概率需要走无头模式 + 虚拟显示（xvfb）。

  ▪ WSL 特殊处理
      scripts/sim/*.sh 里有 WSL 检测逻辑，会设置
      LD_LIBRARY_PATH=/usr/lib/wsl/lib、GALLIUM_DRIVER=d3d12、
      MESA_D3D12_DEFAULT_ADAPTER_NAME=NVIDIA。
      ★ 说明作者主要在 WSL 上开发。AutoDL 是原生 Linux，不触发这段。

  ▪ 场景与规划器坐标必须一致
      autopick 规划器的 8 个障碍物坐标是从 arachne_showroom.sdf
      手工抄写的。★如果你修改 world 文件加物体，规划器不会知道。
      → 你的 Agent 不受此限（因为你会重新设计世界模型），
        但如果你还想让 autopick 能跑（当对照组），改 world 时要同步改
        gazebo_autopick_planner.py 的 _known_obstacles()。

9.3 ★★★ 仿真环境的能力缺口（对你的 Agent 影响最大）
--------------------------------------------------------------------------------

  【缺口一】Gazebo 没有相机
      原因：gazebo_autopick_demo 的 URDF 映射写死 with_ee_camera:="false"，
            且 ros_gz_bridge 没桥接任何图像话题。
      影响：Agent 在 Gazebo 里拿不到任何视觉输入。
      解法：
        ① 改 launch 里的 xacro 映射为 with_ee_camera:="true"
           （要改 Arachne 的代码，你没有推送权限，但可以在本地改后
             不提交，或者在你自己的 launch 文件里重新组装）
        ② 在 ros_gz_bridge 参数里加上图像话题桥接
        ③ ★推荐：在你的 mt001_agent 里写自己的 launch 文件，
           复制 gazebo_autopick_demo 的结构但改这两处。
           这样完全不动 Arachne 仓库。
      ⚠ 但即使加了相机，URDF 里的相机 link 是否配了 gz-sim 的
        sensor 插件还需要核实（在 urdf/sensors/ 下检查是否有
        <sensor type="depth_camera"> 之类的定义）。

  【缺口二】Gazebo 没有 /joint_states
      原因：ros_gz_bridge 没桥接。
      影响：agent_bridge 的机械臂工具直接失效；
            任何需要关节反馈的闭环控制都做不了。
      解法：在你自己的 launch 里给 bridge 加一条 joint_state 桥接。
            ⚠ 具体 gz 话题名需要在 Gazebo 运行时用 `gz topic -l` 查确认，
              通常形如 /world/arachne_showroom/model/arachne/joint_state

  【缺口三】Gazebo 没有 TF
      影响：RViz 里看不到机器人正确位姿；任何坐标变换都要自己算。
      解法：起一个 robot_state_publisher（喂同样的 URDF），
            或桥接 /model/arachne/pose

  【缺口四】Gazebo 没有激光雷达
      URDF 里 with_lidar:="true"（有雷达模型），但桥没接雷达数据。
      影响：做不了 SLAM、做不了动态避障。
      ★ 但 autopick 用的是「已知障碍物列表」，所以它不需要雷达。
        你的 Agent 如果也用已知世界模型，同样不需要。

  ★★★ 综合建议：
     这四个缺口说明【当前 Gazebo 环境是为 autopick 这一个演示定制的
     最小可用环境】，不是通用仿真平台。
     你有两个选择：
       A. 接受现状，Agent 用「上帝视角」世界模型（从 world 文件解析
          物体列表，或直接硬编码），把精力放在决策层。
          ★ 两个月项目推荐这条。诚实地在文档里写明这是简化假设。
       B. 自己在 mt001_agent 里重建一套完整的 Gazebo launch，
          补齐相机、joint_states、TF、雷达四条桥接。
          ★ 工作量约 1-2 周，但会让你的项目更有分量。
          ★ 如果时间允许，值得做——这本身就是可写进 README 的贡献。

9.4 排错速查
--------------------------------------------------------------------------------
  症状                                    → 检查
  ────────────────────────────────────────────────────────────────
  colcon build 报 No module named          → source scripts/env/
    'catkin_pkg'                             arachne_env.sh（conda 劫持）
  arachne_gazebo 编译失败，找不到           → Gazebo 版本不匹配。
    gz-msgs10 / gz-transport13               需要 Garden 而非 Fortress
  launch 报 PackageNotFoundError           → 对应包没编译成功，
    aubo_description 等                      检查 ros2 pkg list | grep arachne
  agent_bridge 报 requires                 → 忘了 motion_enabled:=true
    motion_enabled:=true                     和 confirm_agent_motion:=true
  agent_bridge 报 no complete Aubo         → 没有 /joint_states 数据源
    joint state                              （Gazebo 下必然如此）
  agent_bridge 报 Aubo joint state is      → 状态源停了，或超过 2 秒没更新
    stale: X.XXs
  发了 base_velocity 但 odom 不变           → ① 检查 odom 话题名
                                              （/odom vs /gz/odom）
                                            ② ros2 topic echo /cmd_vel
                                              看指令是否发出
                                            ③ 检查执行层是否在跑
  base_relative 返回 ok 但没动               → grasp_task_server 没启动
                                            （静默失败，见 8.2）
  arm_joint_jog 返回 ok 但没动（mock）      → mock 不订阅
                                            joint_velocity_command
                                            （静默失败，见 8.2）
  ROS 服务调用卡住不返回                     → 检查 FASTDDS_BUILTIN_
                                            TRANSPORTS=UDPv4
  Gazebo 启动后黑屏/崩溃                     → 检查 gz sim --version
                                            检查 nvidia-smi 和 OpenGL
                                            无显示器则改无头模式（见 9.2）
