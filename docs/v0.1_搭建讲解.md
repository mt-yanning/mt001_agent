# v0.1 是怎么搭出来的 —— 逐层讲解与文献对照

写给项目作者自己的学习笔记。目的不是"看懂这些代码"，而是**看懂为什么必须这么分层**，
这样 v0.5 加任务分解、v1.0 加视觉时，你能自己判断新模块该插在哪一层。

文中所有论文节号都是从 `docs/` 里的 PDF 原文核对过的，不是凭印象写的。

---

## 零、一句话概括搭建顺序

> **能动 → 能确认 → 能封装 → 能决策**

自底向上，每一层只依赖它下面那一层。任何一步没做扎实，上面那步都会变成"看起来像在工作"。

```
第 7 步  main.py / check_link.py     跑起来、能自检
           ↑
第 6 步  brain.py                    人话 → 结构化决策        ← LLM 在这里，且只在这里
           ↑
第 5 步  perception.py               世界里有什么             ← v1.0 换成真视觉
           ↑
第 4 步  skills/navigate.py          第一个真技能（闭环）      ← 项目的核心价值
           ↑
第 3 步  skills/base.py              技能契约（三段式）        ← 项目的主要工程量
           ↑
第 2 步  errors.py / utils.py        工程拆分（为了能离线测）
           ↑
第 1 步  primitives.py               发得出去、读得回来
           ↑
第 0 步  读 agent_bridge 源码         定分工线
```

**为什么不能倒过来搭。** 先写 LLM 大脑是最诱人的（那部分最"像 AI"），但如果底下没有
"能确认机器人真的动了"的能力，LLM 就是在对着一个永远回答"好的，做完了"的假机器人做决策。
你会花两周调 prompt，最后发现问题在最底下一层。

## 第 0 步：读 bridge 源码，定分工线

**做了什么**：读 `agent_bridge.py` 的类文档字符串，发现作者写得很明白：

> "The bridge exposes a small JSON tool surface. It **deliberately does not load API keys
> or talk to an LLM provider**; external agent processes call this node **after they have
> made a task decision**."

**得出的决策**：
1. Agent 做成**独立 Python 进程**，用 rclpy 收发话题，**不做成 ROS 包**。
2. 分工线画在"决策"和"执行"之间：桥只管安全执行，推理归我。

**为什么这个决策重要**：它决定了后面所有事。因为 Agent 不是 ROS 包，我不用写 package.xml、
不用 colcon build、改代码不用重新编译 —— 改完直接 `python3 -m agent.main` 就能跑。
对两个月的项目来说，这个迭代速度差别巨大。

**对照文献**：
- **Code as Policies** §III-D "Language Model Programs as Policies" —— LLM 进程与机器人
  控制栈分离，LLM 只产出调用现成 API 的代码，这是同一个分工思想。
- **RoBridge**（你归类图里放在"认知-执行分层"）—— 认知端零训练纯调用，执行端另算。
  它的 IOR 符号中间层就是把这条分工线做得更正式的版本，v1.0 再考虑。

## 第 1 步：`primitives.py` —— 原语层

**解决的问题**：把"和机器人说话"这件事收敛到一个类里，让上层再也不用碰 rclpy。

### 关键设计 1：用事件序号做请求-应答配对

**问题**：bridge 的指令协议**没有 command id**。你发一条 JSON 出去，它在
`/arachne/agent/event` 上回一条 `kind="command_result"`，但这条事件里没有任何字段
能告诉你"我回的是你刚才那条"。

**我的解法**（`call()` 和 `_wait_command_result()`）：

```python
with self._cv:
    seq_before = self._event_seq        # 记下"发之前收到过几条事件"
self._command_pub.publish(msg)          # 发指令
event = self._wait_command_result(seq_before, timeout)   # 等序号更大的那条
```

每收到一条事件就给它编个号存起来，发指令前记下当前号码，然后等一条号码更大的
`command_result`。这在**单客户端、单线程**前提下是可靠的。

> ⚠ 这是个有前提的设计。如果将来 v0.5 要并发发多条指令，这个方案就不够了，
> 那时候要么改成串行队列，要么在 payload 里塞一个自定义字段当 id（bridge 会原样
> 回显在 `payload` 里，可以利用这一点）。**现在先用简单方案，但要知道它的边界在哪。**

### 关键设计 2：状态年龄要两段相加

`_latest()` 这个函数值得单独看：

```python
local_age = time.monotonic() - self._status_stamp   # 我拿到这帧 status 有多久了
total_age = float(item.get("age_sec", 0.0)) + local_age
```

bridge 的 `status.latest.odom.age_sec` 是**它自己**收到里程计数据的年龄。但这帧 status
传到我这里、我再去读它，中间又过了一段时间。**真实年龄是两段之和。**

不这么算会怎样：假设 mock 挂了，bridge 缓存的 odom 停在 1.9 秒前（还没超它的 2 秒线），
而这帧 status 我又拿了 1 秒 —— 实际数据已经 2.9 秒旧了，我却以为它是新鲜的，
然后拿它去做闭环判断。

**对照文献**：**BUMBLE** §III-A 讲感知系统时强调状态的时效性；更直接的是
**IALP** 的 "Grounding Mechanism" 一节 —— 决策必须建立在**当前**世界状态上，
陈旧状态等于没有 grounding。

### 关键设计 3：危险工具在原语层拉黑

```python
FORBIDDEN_TOOLS = frozenset({"aubo_teach", "teach"})
```

`call()` 一进来就检查，`tools()` 返回清单时也过滤。所以 LLM 不是"被提示不要用"，
是**根本看不见**这个工具。

**为什么不靠 prompt**：prompt 是概率性的，工具过滤是确定性的。安全约束不能建立在
"模型应该会听话"上面。`aubo_teach` 在真机上会让机械臂泄力，负载直接砸下来。

**对照**：Arachne `AGENTS.md` 的 Prohibited 一节（"Do not bypass Aubo control ownership /
teach-mode gating"）。这是工程红线，不是论文来的。

### 关键设计 4：`connect()` 上下文管理器保证退出必停

```python
finally:
    client.safe_stop()
    time.sleep(0.2)
```

Ctrl-C、异常、正常退出，三条路都会走到这里。配合 bridge 自己的死人开关
（80 Hz 定时器，`duration_sec` 到期自动归零，最长 2 秒），构成双保险。

**该读的代码**：`agent_bridge.py` 的 `_publish_active_motion()`，看它怎么实现死人开关。
理解它你才知道为什么我发的是**一连串 0.6 秒的短指令**而不是"发一次走 3 米"。

## 第 2 步：`errors.py` / `utils.py` —— 一个纯工程决策

**问题**：`skills/base.py` 本来 `from ..primitives import BridgeError`，而 `primitives.py`
第一行就 `import rclpy`。结果是：**Mac 上根本 import 不了技能库**，连参数校验的单元测试都跑不了。

**解法**：把不依赖 ROS 的东西（异常类、`wrap_angle`、`clamp`）拆到独立模块，
`skills/base.py` 里改用：

```python
if TYPE_CHECKING:            # 只在类型检查时需要，运行时不拉 rclpy
    from ..primitives import BridgeClient
```

**收益**：`python3 tests/test_offline.py` 在 Mac 上直接跑，16 个用例秒过。
你的三环境里 Mac 是唯一随时在手边的，能在上面测东西价值很高。

**这一步没有对应文献**，纯粹是工程手艺。但它体现一个通用原则：
**让"纯逻辑"和"要硬件的部分"可分离**。v1.0 做评测时，这个分离会让你能大批量跑
离线用例而不用开机器人。

## 第 3 步：`skills/base.py` —— 技能契约

### 先搞清楚一件事：为什么 bridge 的 10 个"工具"不是技能

这是整个项目最重要的一个认知，也是你论文里"核心贡献"那一句的依据。

| | bridge 的 10 个工具 | BUMBLE 意义上的技能 |
|---|---|---|
| 例子 | `base_velocity(0.1, 1.0)` | `navigate_to("桌子")` |
| 语义层级 | 以 0.1 m/s 走 1 秒 | 走到桌子那里 |
| 有无反馈 | 发完就完 | 自己判断到没到 |
| 参数来源 | 人给具体数值 | 从语义解析出来 |
| 本质 | **执行器 (actuator)** | **参数化技能 (parameterized skill)** |

BUMBLE 的架构图里，"skill library" 是和 perception、memory 并列的一等公民，
它的每个技能都能接受语义参数、自己执行、自己判断成败。而 Arachne 给你的只有执行器。

> **中间这层是缺的，是需要你造的，也正是论文的核心贡献。**

### 三段式契约

```python
def run(self, ctx, **kwargs):
    cleaned = self.validate(kwargs)          # ① 参数对不对
    self.check_preconditions(ctx, **cleaned) # ② 现在能不能做
    return self.execute(ctx, **cleaned)      # ③ 做，并判断做成没有
```

这三段各自对应文献里的一个机制：

| 阶段 | 论文 | 精确位置 | 它在讲什么 |
|---|---|---|---|
| ① validate | Code as Policies | §III-A "Prompting Language Model Programs" | 给 LLM 明确的 API 签名（Hints / Examples），并保证它产出的调用是合法的 |
| ② check_preconditions | **IALP** ★主蓝本 | "Methodology → **Feasibility**" | 六个可判定谓词：find / at / detected / graspable / placeable / reachable |
| ② check_preconditions | **ConceptAgent** ★主蓝本 | §III-C-1 | 前置条件由 LLM 自动生成 + `F(s,P)∈{0,1}` 形式化验证 |
| ② check_preconditions | IALP | "Problem Formulation → Grounding Mechanism" | 决策必须建立在当前世界状态上 |
| ② check_preconditions | SayCan ⚠仅思想 | 正文 "SayCan" 节 | 「该做 × 能做」的分离。⚠ 其 affordance 是 RL 训练的 value function，免训练路线不可用 |
| ③ execute + 判成败 | ConceptAgent | §III-B "LLM-guided Tree Search with **Self-Reflection**" | 失败反馈与恢复 |

### v0.1 做到哪、没做到哪（诚实标注）

`check_preconditions` 现在只做**硬布尔判断**（运动开关开没开、里程计新不新鲜）。

#### ⚠ 重要修正：别拿 SayCan 当可行性检查的主参考

SayCan 的公式是 `π = arg max_π p(c_π|s,ℓ_π)·p(ℓ_π|i)`，两个概率相乘。但它的
affordance `p(c_π|s,ℓ_π)` 是**用 RL 训练出来的 value function**（BC-Z / QT-Opt）。

**本项目走免训练路线，这个机制照抄不了。** SayCan 的价值是它第一个把"该做"和
"能做"两个维度分开——这个 framing 写论文要引，但**机制要去 2025 的两篇里找**。

#### v0.5 可行性检查的真正蓝本

| 来源 | 机制 | 为什么适合本项目 |
|---|---|---|
| **IALP** (AAAI'25) | 六个可判定谓词 + PDDL 前置条件集合全 True 才执行 | 同为 mobile manipulation；四个谓词现在就能实现 |
| **ConceptAgent** (ICRA'25) | 前置条件由 LLM 自动生成；`F(s,P)∈{0,1}` 形式化验证 | 技能库会一直加技能，手写前置条件不 scalable |

**IALP 的六谓词与本项目的对应**（原文 Methodology → Feasibility 一节）：

| 谓词 | IALP 的实现 | 本项目的实现 | 何时可做 |
|---|---|---|---|
| `at` | 假设执行后到达目标 | odom | ✅ 已有 |
| `find` | voxel map + CLIP + A* | **抄 autopick 的 A* + 已知障碍物列表** | ✅ v0.5 |
| `reachable` | 查预计算 reachability map | **`AuboI5Kinematics.solve_position` 收不收敛** | ✅ v0.5（白送） |
| `detected` | LangSAM 抠 mask | 上帝视角桩里 = 在不在物体列表 | ✅ v0.5 |
| `graspable` | GraspNet + LangSAM 过滤 | 需要真实感知 | v1.0 |
| `placeable` | 点云分割 + 中位坐标 | 需要真实感知 | v1.0 |

> ★ `reachable` 尤其划算：v0.5 的 `reach_to(xyz)` 本来就要调 `solve_position`，
> **IK 不收敛 = 够不着 = 前置条件不满足**。SayCan 要训一个 value function 才能
> 回答的问题，这里一次 IK 求解就答了。

**ConceptAgent 的前置条件自动生成**（原文 §III-C-1）：

```
P_i = LLM(系统提示 S, 动作名 n_i, 动作描述 d_i, 属性列表 atts)
F(s_t, P_c) = 1 → 执行；= 0 → 判定不可行，中止并给恢复反馈
```

本项目的 `Skill` 基类已经有 `name` / `description` / `args_schema` 三个字段，
**正好就是喂给 LLM 的那三样输入**，接口现成对得上。

**IALP 的 Optimality**（候选排序）：LLM 生成 K 个候选动作，按各自语言描述的
token log 概率之和排序，取最高者 `a*_t = arg max p_t(a^k_t|i,D,P)`。

> ⚠ **这条有依赖**：需要 API 返回 logprobs，DeepSeek / 通义的 OpenAI 兼容接口
> 不一定提供。到 v0.5 时先测。拿不到就降级成 ConceptAgent 的 critique scoring
> （让 LLM 自己给候选打分），两条路殊途同归。

#### 一个结构性观察

**BUMBLE 没有独立的可行性模块**（§III-A 是感知/技能库/记忆，§III-B 是决策），
它靠 VLM 自身判断 + 失败恢复来兜。所以三篇不是竞争关系：

> BUMBLE 给整体骨架 → IALP 补可行性谓词 → ConceptAgent 补前置条件自动化与失败归因

#### 失败归因需要历史（ConceptAgent §III-C 的洞见）

> 搜柜子失败，可能是柜子没开、可能是没走到够得着的距离、可能是手上已经拿着东西。
> **必须结合规划历史才能判断，光看这一步的失败信号推不出来。**

这解释了为什么 BUMBLE 的短期记忆和失败恢复是绑在一起的——**没有历史就没法归因**。
所以 v0.5 的 `memory.py` 不是可选项，它是失败恢复的前置依赖。

> 📌 **写论文时的诚实标注**：v0.1 的可行性检查是硬布尔版本；IALP 式的谓词化
> 与 ConceptAgent 式的前置条件自动生成在 v0.5 引入。

## 第 4 步：`skills/navigate.py` —— 第一个真技能

这个文件是整个项目**技术含量最高**的一处，也最该逐行读懂。

### 拆成三个子问题

**(a) 怎么走** —— 先转向后前进的两段式 P 控制器：

```python
if abs(heading_error) > yaw_tolerance:
    angular = clamp(k_angular * heading_error, max_angular)   # 只转不走
else:
    linear = clamp(k_linear * distance, max_linear)           # 走，带小幅纠偏
```

为什么不边走边转：差速底盘边走边大角度转会画弧线，路径不可预测。先对准再走，
轨迹是可预期的直线段，出问题好排查。

> 对照 autopick：它用的是 **A\* + 纯追踪（Pure Pursuit）**，`lookahead_distance=0.46`。
> 那套更平滑，但需要完整的已知障碍物地图。v0.1 场景空旷，两段式够用；
> v0.5 要绕桩时可以把 autopick 的 A\* 搬过来当一个 `plan_path` 工具。

**(b) 走多久** —— 每步 0.6 秒，然后重新读状态再决定下一步。

上限是 bridge 的 `max_base_command_duration_sec = 2.0`。发一条长指令然后撒手，
在 Agent 崩溃时机器人会继续走满 2 秒；发短指令串则最多多走 0.6 秒。
**同时它天然形成了"感知-决策-执行"的控制周期**，这正是闭环的形状。

**(c) 怎么确认真的动了** —— 这是核心：

```python
before = ctx.bridge.odom()
result = ctx.bridge.call("base_velocity", ...)
data = result.get("data") or {}
actual_duration = float(data.get("duration_sec", duration))   # ★ 读实际生效值
sleep(actual_duration + 0.25)
after = ctx.bridge.odom()
```

**两个容易漏掉的点：**

1. **期望位移必须用回执里的实际值算**，不能用我发出去的值。bridge 的限幅是**静默**的：
   发 `linear_x=100` 会被悄悄改成 0.20，发 `duration=9999` 会被夹到 2.0，
   它不报错、不警告。用发出去的值算期望，会把"正常执行"误判成"没动"。

2. **连续 3 步位移不到期望的 25% → 判定静默失败**，停下并报告最可能的四个原因。

### 为什么这一条是项目的核心卖点

架构审查里那张三环境可用性矩阵得出的结论是：

> `base_relative` / `base_turn` 在仿真下没有订阅者，指令发出去消失了，
> bridge **照样返回 `ok:true`**；`arm_jog` 在 mock/Gazebo 下也没人订阅它的输出话题，
> 同样 `ok:true` 但机械臂不动。

也就是说，**在这套系统上，"指令被受理"和"动作被执行"是两件事，而且没有任何机制
告诉你它们不一致。** autopick 完全没处理这个问题（它是开环的，压根不读反馈）。

| autopick 的做法 | 我的做法 |
|---|---|
| 不读 `/joint_states`，自己在内存里维护"我以为的关节角" | 每步读回 odom 实测 |
| 状态机单向推进，没有回退分支 | 判定失败 → 停 → 报告原因 |
| 抓空了、撞上了都不知道，继续往下走 | 连续 3 步无位移就判定并终止 |

**对照文献**：
- **RoBridge** —— 闭环判成败（成功/错误/正常三态）
- **ConceptAgent** §III-B —— 失败反馈与自反思
- **BUMBLE** —— 失败恢复
- **SayCan** —— affordance 的"事后版本"：SayCan 是**事前**估计能不能成功，
  我这里是**事后**验证到底成没成。v0.5 把两者接起来（事后结果喂回事前估计）就是记忆。

## 第 5 步：`perception.py` —— 世界模型桩

**做了什么**：解析 `arachne_showroom.sdf`，把 16 个模型的坐标读出来，附上中文别名。

**为什么是桩**：当前 Gazebo 演示的 URDF 映射写死了 `with_ee_camera:="false"`，
且 `ros_gz_bridge` 没桥接任何图像话题 —— **物理上就拿不到图像**。

**关键设计：接口形状照着 v1.0 设计**

```python
def find(self, query: str) -> SceneObject | None:
    ...
    return None          # 找不到就返回 None，不瞎给一个
```

这个 `None` 是 v1.0 **拒答能力的地基**。大脑拿到 `None` 就输出 `skill: "none"`，
明确说"场景里没有这个东西"，而不是编一个坐标把机器人开到墙里。

**对照文献**：
- **DynaMem**（ICRA'25）—— "负结果拒答 + 价值图探索"。找不到目标时明确报告未找到，
  并触发主动探索，而不是硬抓。v0.1 只做了前半句（拒答），后半句（探索）在 v1.0。
- **BUMBLE** §III-B a) —— 它的感知用 **Set-of-Mark (SoM) prompting**：把检测框标上数字，
  让 VLM 选 ID，而不是让 VLM 直接输出坐标。**这是 v1.0 替换本文件时要照抄的做法**，
  因为 VLM 报坐标很不准，但选 ID 很准。

> 📌 **第二个必须诚实标注的简化**：v0.1 的"感知"是上帝视角，不是感知。
> 文档里要写清楚，这既是学术诚实，也是给评审看你知道自己在简化什么。

## 第 6 步：`brain.py` —— LLM 大脑

### 关键设计 1：强制"先想后答"

提示词要求输出：

```json
{"think": "推理过程", "skill": "技能名", "args": {...}}
```

**对照 ManipLVM-R1**：它的输出格式是 `<think>Reasoning</think><answer>...</answer>`，
强制模型先写推理再给答案。我用 JSON 字段实现同一件事。

**为什么有用**：一是推理质量确实会提升（思维链效应）；二是**调试时你能看懂它为什么
这么决定**。当机器人开错方向，`think` 字段会告诉你它是算错了落脚点，还是认错了物体。

### 关键设计 2：JSON 抽取要抗造

`extract_json()` 做了括号配平扫描，能从 ```` ```json ```` 代码块、前后废话里把
第一个完整对象抠出来，还能正确处理字符串里的 `{}` 和转义引号。

**为什么必须这么做**：模型会画蛇添足。`json.loads()` 直接调用的成功率在实际使用中
很难到 100%，而每失败一次就是一次白花的 API 调用和一次糟糕的用户体验。

### 关键设计 3：提示词里的规则 4 和 5

```
4. 需要走到某个物体那里时，不要直接把物体坐标当作目标点 —— 机器人有体积，
   应该停在距离它约 0.6 米的位置。
5. 如果指令说的物体不在场景列表里…就把 skill 设为 "none"…不要瞎猜坐标。
```

规则 4 是**领域知识注入**：LLM 不知道机器人有半径 0.48 米。
规则 5 是**拒答开关**，对应 DynaMem。

**对照 Code as Policies** §III-A "Prompting Language Model Programs" —— 它把提示词
拆成 **Hints**（import 语句，告诉 LLM 有哪些 API）和 **Examples**（指令-代码对，few-shot）。
我现在只有 Hints（技能 schema 是自动从代码生成的），**没有 Examples**。

> 📌 **一个明确的改进点**：CaP 的实验显示 few-shot 示例对代码生成质量影响很大。
> 你可以在 `single_step.txt` 里加 2-3 个"人话 → JSON"的示例对，很可能直接提升准确率。
> 这是个成本极低、见效很快的实验，适合当你的第一个消融对照。

### 关键设计 4：`ScriptedBrain`

不联网的替身。用途：单元测试，以及还没配 API Key 时先验证 ROS 链路。
这是"依赖注入"的常规做法，但对你后面做**评测**很关键 ——
v1.0 要统计成功率时，你需要能把大脑换成固定脚本来做对照组。

---

## 第 7 步：`main.py` + `scripts/check_link.py`

`check_link.py` 是把架构文档里"组合 A 的手工六步"自动化。**它比 main.py 更重要**，
因为它是你排查问题时的第一道工具：八项里哪一项红了，直接定位到是哪一层出问题。

分层排查的价值：链路自检全绿之后，如果 `main.py` 表现不对，你就知道**问题一定在
LLM 决策层**，不用再怀疑 ROS 通信、话题名、安全开关。这能省掉大量瞎猜的时间。
